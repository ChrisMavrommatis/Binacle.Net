# Every folder explains itself

Two lines, and the second is the one that needs judgement:

- **Every folder at the repo root has a `README.md`.** No argument about significance - it is a root folder,
  so it gets one.
- **A folder below the root has one when it is significant.** `api/` yes, `api/requests/` yes,
  `api/src/` and `api/test/` no.

## Significant means a reader arriving cold needs it

Write one when any of these is true:

- It is **a thing you could open on its own** - a project, a package, a gem, a site, a tool.
- Its files are **edited or regenerated by hand**, and getting that wrong is expensive - fixtures, test
  vectors, committed data, sample stacks, deploy config.
- It has **its own commands** - something you run, serve, or verify that nothing else in the tree runs.
- Something in it is **surprising** - a layout convention, a rule that must hold, a file that looks
  generated and is not.

Skip it when:

- The folder name is **language or framework furniture** - `src/`, `test/`, `Models/`, `Services/`,
  `Properties/`, `ExtensionMethods/`, `Tests/`, `Providers/`.
- **The parent already says it** in a table row, and the row is enough.
- It is **generated output** or **vendored third-party code**. The folder that holds it explains it once.

A folder that fails every test above and still feels like it needs a page is usually telling you the parent
README is thin. Fix the parent first.

## The parent indexes, the child explains

Every README lists its own subfolders, one row each, saying what each is. That row is the whole documentation
of a child that needs no page of its own. A child gets its own page only when the row cannot carry it - and
then the row stays, pointing at it.

The same fact is never in both. The parent says what the child is; the child says how it works.

## Shape

A person just opened this folder and does not know the project. In order:

1. **What it is** - one or two sentences, plain.
2. **What is in it** - a `Folder | What it is` table. This is the part people actually read, so it comes early.
3. **How you use it** - the commands, from the repo root, in a fenced block.
4. **What will bite you** - the gotchas, last, in prose.

Two paragraphs is a fine README. Nothing here asks for length.

## Style

- **Headings carry an icon** - `icon-headings-in-public-docs.md` has the icon set and the one-per-heading rule.
- **Write for the human, not for us.** Say what a person opening the folder wants to know. Anything that only
  an agent needs belongs in `.agents/`, not here.
- **Link real paths** - the file next door, the parent, the root `README.md`. Never point into `.agents/`;
  `who-references-whom.md` is the full matrix.
- Plain language, and cut every word that does not change the meaning.

## Three carve-outs

- **The repo root `README.md` is the landing page**, not a folder index. This rule does not reach it - it is
  the most-read file in the project and is edited on purpose, never in passing.
- **`.github/` gets no `README.md` of its own.** GitHub shows `.github/README.md` *instead of* the root one, so
  adding it silently replaces the project's landing page. Document that slice one level down, in
  `.github/workflows/README.md` and `.github/actions/README.md`.
- **Folders that are not ours** - `node_modules/`, `.idea/`, anything a tool creates and gitignores whole -
  get nothing. A gitignored folder we do own keeps its README committed, `artifacts/` being the example: the
  folder is empty on a fresh clone and the README is the only thing that says what lands there.

**Why:** a folder with no README makes every reader reconstruct it from filenames, and they each guess
differently. The tables and icons are not decoration - they are how someone finds the one row they came for
without reading the page.
